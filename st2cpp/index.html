st2cpp Released · v0.4

A transpiler that compiles IEC 61131-3 Structured Text into clean, native C++17 — validated by a complete semantic analysis stage and driven by JSON-defined data and external libraries. No virtual machine, no interpreter — just auditable, standard C++ you can compile, debug, and ship anywhere.

Overview

st2cpp is the compiler component of the undoRT ecosystem. It takes .st source files and produces .hpp / .cpp pairs that compile with any C++17-capable toolchain.

Before any code is emitted, your program is checked, not just parsed: a two-pass semantic analysis verifies symbols, scopes, types, array bounds, inheritance and interfaces, and process-image addresses — catching at build time the errors that would otherwise surface on a live plant.

And while st2cpp reads Structured Text, it speaks JSON: libraries, data types, variables, dependencies and C++ bindings are declared in standard, versioned JSON descriptors that the toolchain can both import (external libraries, project configuration) and export (ST → library descriptor → JSON) with a guaranteed round trip.

  • Full semantics — two-pass analysis, IEC case-insensitive resolution, type checking
  • Fail-fast --strict mode for CI and production builds
  • All IEC 61131-3 elementary types, STRUCT, ENUM, arrays, pointers, interfaces
  • FUNCTION / FUNCTION_BLOCK / PROGRAM, FB inheritance with SUPER^
  • Named & positional calls, VAR_OUTPUT binding via =>
  • Method visibility (PRIVATE, PROTECTED, PUBLIC)
  • Process Image %I/%Q/%M with auto-detection
  • External libraries & data in JSON — Library Descriptor v1.0
  • ST → JSON export: semantic-only library descriptors with round trip
  • Modular project generation with automatic dependency sorting
  • Header-only runtime (zero dependencies), single binary, no install
v0.4 highlights: semantic analysis is production-ready, external libraries and project configuration are defined in versioned JSON, and the compiler now exports ST back to JSON library descriptors. Your tests count is now 663 automated tests, executed on every commit.

Quick Start

# Transpile a single file
./st2cpp program.st --namespace myplc

# Transpile an entire workspace in project mode
./st2cpp --workspace ./src --project-style --output-dir build --namespace myplc

# Wire in external libraries declared in JSON
./st2cpp --workspace . --ext-libs project.json --namespace myplc

# Fail-fast semantic validation for CI
./st2cpp program.st --strict

# Compile the generated C++
g++ -std=c++17 -I./st2cpp_includes build/Programs/Main.cpp -o plc_main

Semantic Analysis — Code You Can Trust

St2cpp doesn't stop at parsing. Every source is analyzed before code generation: the analyzer builds a full symbol table with case-insensitive IEC 61131-3 identifier resolution, resolves type references across scopes, and checks assignments, calls, array indices, and member accesses for type compatibility.

Because PLC programs run critical equipment, errors are surfaced at compile time with precise file:line:col diagnostics and stable error codes — so a semantics failure never becomes a runtime failure on your controller.

Two-Pass Analysis

  • First pass — registers every enum, struct, interface and POU header with a stable type id, so forward references (a struct or FB that uses a type declared later) resolve correctly.
  • Second pass — resolves every body: names, types, expressions, calls, members.
  • Declaration-order independent — the result is identical no matter how your files are ordered after a workspace merge.
  • Circular dependency detection — by-value cycles (A contains B contains A) are reported; pointer / REF_TO cycles stay legal, as in IEC.
  • Inheritance & interfaces — EXTENDS/SUPER^ resolution and IMPLEMENTS contract verification (abstract methods, overrides).
  • Enums are typed — enumerators carry their enum type, usable in assignments and comparisons.

Strict vs Permissive Modes

ModeBehaviourBest for
Permissive (default) Collects diagnostics, surfaces them with --verbose, but still generates, gracefully falling back to legacy inference Incremental adoption on existing codebases
Strict (--strict) Prints every diagnostic and blocks generation as soon as any error is found CI pipelines, production and safety-critical builds

Process Image & AT Addresses

Globals mapped with AT %I…, AT %Q… and AT %M… are resolved and validated against the configured process image layout, and accessors are generated for bit, byte, word and dword sizes. --pi-auto detects the image size automatically; leave it on for zero-config I/O, or use --pi-input/output/marker to pin exact sizes.

Data-Driven by Design — Everything Is JSON

Libraries, data types and projects are data, not code. st2cpp ships a self-contained JSON engine and two versioned schemas, so your engineering data survives between tools, versions and teams — and the compiler both consumes and produces it.

Library Descriptor JSON v1.0

A Library Descriptor declares one library: identity (id, name, semver version), dependencies, and the resources it exposes — constants, enums, types (structs), globalVariables, functions and functionBlocks — each with typed references, initializers and, when available, the C++ binding to back them. 

{
  "$schemaVersion": "1.0",
  "id": "io",
  "name": "I/O Library",
  "version": "1.0.0",
  "enums": [{
    "name": "AlarmMode",
    "baseType": { "kind": "primitive", "name": "INT" },
    "members": [
      { "name": "Off", "value": 0 },
      { "name": "On",  "value": 1 }
    ]
  }],
  "globalVariables": [{
    "name": "factoryAlarm",
    "type": { "kind": "named", "name": "AlarmMode" },
    "scope": "global"
  }]
}

The loader validates structure and cross-entity rules (unique names, resolvable references, valid initializers, coherent bindings) and returns all problems at once, not just the first one. A canonical serializer round-trips the descriptor to byte-identical JSON.

Project Configuration JSON v1.0

A project.json lists the libraries a project uses. One --ext-libs flag on the command line loads the registry, injects the external symbols into semantic analysis, and makes the code generator emit namespace-qualified calls, FB instance methods and the required #includes automatically. 

{
  "$schemaVersion": "1.0",
  "libraries": [
    { "id": "io",       "path": "libraries/io.json" },
    { "id": "math",     "path": "libraries/math.json" }
  ]
}

Import & Export — a Closed Loop

The pipeline is bidirectional. Beyond importing JSON libraries, st2cpp exports analyzed Structured Text back to a semantic-only Library Descriptor through LibraryDescriptorBuilder: 

ST ──▶ Parser ──▶ SemanticAnalyzer ──▶ LibraryDescriptorBuilder ──▶ JSON (v1.0)
        ▲                                                                  │
        └─────────────── re-import (round trip) ◀── LibraryLoader ◀────────┘
  • Semantic-only descriptors — valid without C++ bindings (functions and FBs may omit cppBinding).
  • Unrepresentable constructs produce explicit, named errors — never silent omissions.
  • Dependencies are derived from analysis and validated against version policies.
  • Deterministic output: same ST + same options ⇒ byte-identical JSON.
st2cpp lib.st --export-descriptor lib.json \
    --lib-id timerlib --lib-name TimerLib --lib-version 1.0.0

The export command runs on a single .st file or on a whole --workspace (merged as one library), composing with --ext-libs so external references become real dependencies with explicit version policies (--lib-dependency <id>=<constraint>). Unrepresentable constructs are reported as Export error lines, never silently dropped.

External Libraries in Action

st2cpp --workspace . --ext-libs project.json --output-dir generated

Symbols from the declared libraries resolve during analysis, and the generated C++ calls compile against the referenced C++ (or other ST libraries) with the right namespace and includes — a clean boundary between your logic and third-party or native code, driven entirely by data.

Method Visibility

st2cpp supports PRIVATE, PROTECTED, and PUBLIC visibility modifiers for methods inside FUNCTION_BLOCK.

ST Syntax

FUNCTION_BLOCK MyFB
    VAR
        counter : INT;
    END_VAR

    METHOD PRIVATE splitMix : UDINT
        VAR_IN_OUT state : UDINT; END_VAR
        // ...
    END_METHOD

    METHOD PROTECTED init : BOOL
        // ...
    END_METHOD

    METHOD PUBLIC exec : UDINT
        VAR_INPUT N : UDINT; END_VAR
        // ...
    END_METHOD
END_FUNCTION_BLOCK

Generated C++

struct MYFB {
public:
    // Variables...
    // SETTER/GETTER...

    // --- PRIVATE METHODS ---
private:
    virtual UInt32 SPLITMIX(UInt32& STATE);

    // --- PROTECTED METHODS ---
protected:
    virtual Bool INIT();

    // --- PUBLIC METHODS ---
public:
    MYFB();
    void operator()();
    virtual UInt32 EXEC(Int16 N);
    virtual ~MYFB() = default;
};
Default visibility: Methods without explicit visibility default to PUBLIC. Constructor, operator(), and destructor are always PUBLIC.

Single File Mode

The default mode. Produces one .hpp and one .cpp from a single .st source. Best for small projects or quick experiments. 

./st2cpp counter.st -o counter.cpp -H counter.hpp --namespace myplc

Include the undoCore/ runtime (shipped in the st2cpp_includes/ folder) in your compiler's include path when building the output: 

g++ -std=c++17 -I./st2cpp_includes counter.cpp -o counter

Project Mode

For workspaces with multiple POUs. st2cpp scans all .st files recursively, resolves dependencies between Function Blocks via topological sort, and generates a circular-dependency-safe header layout: 

./st2cpp --workspace ./plc_src --project-style --output-dir build --namespace myplc
build/
├── SimpleGVLs.hpp        # ENUMs, simple STRUCTs, simple globals
├── FunctionBlocks.hpp    # Aggregator — includes all FB headers
├── FunctionBlocks/       # One .hpp/.cpp per Function Block
│   ├── Timer.hpp / .cpp
│   └── Counter.hpp / .cpp
├── GVLs.hpp / .cpp       # Complex globals (STRUCTs containing FBs)
├── Functions.hpp / .cpp  # Global functions
└── Programs/
    └── Main.hpp / .cpp
Use project mode for any workspace with more than 2–3 Function Blocks. It enables incremental compilation and keeps each FB as a separate file in your IDE.

Full Example

Input (counter.st)

FUNCTION_BLOCK Counter
    VAR_INPUT
        Enable : BOOL;
        Reset  : BOOL;
    END_VAR
    VAR_OUTPUT
        Count : INT;
    END_VAR

    IF Reset THEN
        Count := 0;
    ELSIF Enable THEN
        Count := Count + 1;
    END_IF
END_FUNCTION_BLOCK

PROGRAM Main
    VAR
        C : Counter;
    END_VAR

    C(Enable := TRUE, Reset := FALSE);
END_PROGRAM

Generated header (counter.hpp)

#pragma once
#include "undoCore/undoCore.hpp"

namespace myplc {

// FUNCTION BLOCK COUNTER
struct COUNTER {
public:
    // VAR_INPUT
    Bool ENABLE{};
    Bool RESET{};
    // VAR_OUTPUT
    Int16 COUNT{};

// SETTER/GETTER
    inline void set_ENABLE(Bool val) { ENABLE = val; }
    inline void set_RESET(Bool val) { RESET = val; }
    inline Int16 get_COUNT() const { return COUNT; }
// End SETTER/GETTER

    COUNTER();
    void operator()();
    virtual ~COUNTER() = default;
};

// PROGRAM MAIN
struct MAIN {
    COUNTER C{};

    void run();
};

} // namespace myplc

Generated source (counter.cpp)

#include "counter.hpp"

namespace myplc {

// FUNCTION BLOCK COUNTER
COUNTER::COUNTER() {}

void COUNTER::operator()() {
    if (RESET) {
        COUNT = 0;
    } else if (ENABLE) {
        COUNT = COUNT + 1;
    }
}
// END FUNCTION BLOCK COUNTER

void MAIN::run() {
    C.set_ENABLE(true);
    C.set_RESET(false);
    C();
}

} // namespace myplc

Architecture

st2cpp follows a classic compiler frontend pipeline — hand-written in C++17, no external parser generators — extended with a semantic analysis stage and a bidirectional JSON data layer: 

ST Source
  └─▶  Lexer            (Token stream)
         └─▶  Parser         (Recursive descent → AST)
                └─▶  SemanticAnalyzer   (2 passes → symbol table, diagnostics)
                       └─▶  CodeGen       (AST + semantics → C++17 source)

JSON side:
  Project Config / Library Descriptor (v1.0)
    └─▶  LibraryLoader / LibraryRegistry ──▶ SemanticAnalyzer (external symbols)
    └─▶  LibraryDescriptorBuilder ────────▶ JSON export (ST → descriptor)

The AST uses std::variant for node types (ExprVariant, StmtVariant) with std::visit dispatch — no virtual dispatch, no dynamic_cast.

🔗 Integration with undoCore: The generated code includes #include <undoCore/undoCore.hpp> and uses STArray, VAR_INOUT, and conversion functions from the undoCore library.
